PERSONAL / FUTURE

個人・作業メモリ

個人情報や作業固有の文脈。ユーザー単位／ワークスペース単位のSQLiteを候補にする。

管理単位：個人・ワークスペース

保存場所だけで権限を保証しない。誰が読めるか、外部送信できるかは別途設計。

NASへ広げる場合は？

共有領域を「NAS上のNGRサービス＋NAS内のローカルSQLite」へ移す案。各PCがネットワーク共有ファイルを直接開く方式は採らない方向。クライアントはサービスへ接続する。

個人DBまでNASへ移す必要はない。対応CPU、認証、バックアップ、同時書き込みの制御は将来設計する。

クラウドとローカルの関係はどう持つ？

オンライン文書の識別子や版への参照を、ローカル判断の関係として保持する案。本文・全ベクトルの一括複製は不要。ただし識別子の安定性、削除・権限変更、古い参照の扱いは未決定。

033つのランキングではなく、判断に使える根拠を返す

  1. 問いと条件を受け取る

    何を知りたいか、対象、除外条件、使える領域を確認。検索回数や返却量にも予算を設ける。

  2. 入口となる情報を探す

    GitHub知識ならクラウドのキーワード＋意味検索。過去の判断が主題ならローカルから始める。常に全経路を動かすとは限らない。

  3. NGRが関係を活性化する

    前提・依存・反証・失敗経験などへ探索を広げる。単なる類似度とは別に「今、確かめる価値のある情報」を選ぶ。活性化の計算規則は未決定。

  4. 小さな根拠セットへまとめる

    重複を除き、短い抜粋・出典・関係・詳細取得IDを返す。直接の答えだけでなく、重要な反証や条件も残す。件数ではなく合計トークン量も制御する。

  5. 足りない部分だけ追加探索する

    エージェントが不足・矛盾・古さを検討し、必要な本文や関係だけを追加取得する。十分な根拠が得られた時点、または予算上限で停止する。

  6. 実際に使った結果を分けて記録する

    取得・選択・検証・使用・結果を混同しない。利用結果を後の活性化へどう反映するか、個人と共有のどちらへ残すかを設計する。

グラフの価値が出る例 — 動作実績ではなく設計例
実装案A → 前提Bに依存 → Bは変更済み
実装案A → 過去の失敗 → 原因Cは今回も存在

「Aの関連記事を増やす」だけではなく、Aの採用を見直し、BやCを確認する問いにつなげる。

活性化が強い ≠ 正しい。確認する価値が高い、という手掛かり。

ローカル判断・個人メモリの学習済みベクトル検索は未決定。クラウドへ接続するだけで、これらが自動的に意味検索できるわけではない。

PyInstallerPython・依存を同梱

配布パッケージインストーラー形式は未決定

PyInstallerは主にパッケージ化。高速化のためのネイティブコンパイルではない。配布物そのもので起動・SQLite・MCP接続を検証する。GitHub Actionsでのビルドと、公開リリースの承認は別工程。

利用者の初回導入

  1. NGRをインストールし、DBを準備
  2. 既存github-ragへ接続、または自分のCloudflareへ新規配置
  3. 必要に応じてGitHub Appと対象リポジトリを承認
  4. AIのMCP接続を設定し、接続テスト

既存環境の利用者にクラウドの作り直しを要求しない。管理者権限をAIへ渡す前提にしない。

初期設定を軽くする候補

  • Deploy to Cloudflareボタンによる配置
  • GitHub App Manifestによる登録支援
  • コールバックURL等の手入力削減
  • 対応AIごとの接続設定支援

いずれも統合セットアップへの組み込みは未実装。利用者の承認・料金条件・新規リポジトリ作成の有無を導入画面で示す。

無料配布と署名・更新

アプリを有料化する予定はない。有料コード署名の契約を前提にしない。試作と一般公開を分け、OSS向け無償署名の利用条件を後で確認する。

署名なしの配布物は環境によって警告・実行制限があり得る。利用者に保護機能の解除を求める設計にはしない。署名・インストーラー・更新の真正性確認・失敗時の復旧・DB移行前のバックアップは未決定。

06どこまで決めたか

区分内容
方針決定Pythonを継続。Actions＋PyInstallerで実行環境を同梱。Windowsはユーザー単位の常駐ランチャーを入口にする。
基本方向クラウドのgithub-rag方式を維持。共通知識・判断履歴は共有SQLite。個人／作業メモリは別領域。利用窓口を統合する。
設計対象ノードと関係の定義、活性化・抑制・減衰、反証の扱い、利用結果の反映、取得予算と停止条件。
設計対象クラウド接続契約、参照IDと版、MCPの操作体系、権限と外部送信、ローカル意味検索、同時書き込みの制御。
詳細未決定GUI技術、プロセス分離、MCP通信方式、自動起動、インストーラー、署名、更新、DB移行と復旧。
将来候補NAS／Linuxサーバー上のNGRサービス、個人メモリ連携。一般利用者にサーバー所有を要求しない。
今回不採用クラウドの全文書・全ベクトルをローカルへ差分同期する構成。現時点では同期実装の負担が大きい。
初期対象外全面的なTypeScript移植、Windowsサービス必須化、ブラウザ専用UI、ローカル大型モデルの必須化。

次の設計の中心：グラフが「検索候補の追加」を越えて、判断に必要な情報をどう活性化するか。

この資料は対話で合意した方向と候補を整理したもの。検索性能、統合後の効果、配布互換性を保証するものではない。既存の実験記録・共有DB・NGRソースは変更していない。
